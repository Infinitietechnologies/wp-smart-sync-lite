# Bounded sync-status polling

Active-upload local-server timeout: a live run had processed 31/102 files while its status XHR failed at 15 seconds. A batch can run for 20 seconds and individual provider calls can take longer; PHP's built-in server cannot answer the queued status request until the worker request yields. Localization now gives all three status owners a 180-second timeout only under `cli-server`, retaining 15 seconds elsewhere. There is still only one in-flight status request. A timeout preserves the active run and reports delayed status as a warning rather than an upload failure. Idle/terminal polling suppression, retry limits, and authentication handling remain in effect. The native `local-status-server-browser.cjs` fixture confirms that a real status XHR waits behind a 17-second operation, succeeds beyond the old cutoff, and retains running progress. No production upload is used. This accommodates queueing; it cannot make a single-request server provide simultaneous progress updates. Client version: `local-status-wait-1`.

Local-server follow-up: the Windows development site uses PHP's single-request built-in server. Wizard status requests could be queued behind provider discovery/configuration and hit the 15-second client timeout. The wizard now defers new status requests while a provider operation is pending, then coalesces them into one check after it finishes. Existing in-flight status responses retain their concurrency guards. Tests cover successful/failed discovery, deferred refresh signals, an already-pending active-run response, and Google credential cleanup during saving. The native six-provider browser workflow passes. Wizard cache version: `deferred-status-1`.

Implemented 27 October 2026 in the maintained and installed plugins. No commits created.

Follow-up fix: the local site reported a completed zero-file run with no active lease, but window focus/visibility/connectivity events still issued status requests. All three owners now keep known inactive states quiet through those events. Initial page loading, explicit refresh, BFCache restoration, and start/stop signals can still check status. A hidden cross-tab signal invalidates the cached status so it is checked on return. Active or unknown states still resume normally. If cross-tab storage is unavailable, reload to discover work started elsewhere. Verified by 117 admin cases and the browser's focus/visibility/reconnect burst followed by two simulated minutes without new status requests. Client cache versions are `idle-polling-2`.

| Issue | Cause | Fixed | How |
| --- | --- | --- | --- |
| Failed/completed runs kept requesting status | Main settings, the cloud wizard and the standalone widget scheduled another check even after terminal/idle responses. | Yes | Check once initially, then repeat only while processing or while a valid shared operation lease is finishing. Settled idle/completed/failed responses schedule no more status requests. Failure notifications remain visible independently. |
| Connection failures retried indefinitely | Every failed request scheduled the same short retry interval. | Yes | Back off for 5, 10, 20 and 40 seconds, then pause after the fifth consecutive failed attempt. HTTP 401/403 pauses immediately. Main settings/the standalone widget provide Check status; the wizard explains that reload/return can check again. Successful responses reset the failure budget. |
| Hidden/offline pages continued making requests | Poll timers did not consider page visibility or connectivity. | Yes | Clear scheduled checks on hide/offline, and suppress new requests while hidden/offline. A return to the visible page, window focus, reconnect or BFCache restore performs a fresh check. Background transfers continue independently. |
| Status checks could overlap | Several recovery/navigation/action callbacks could issue a request while one was pending. | Yes | Each existing page owner now keeps one in-flight request. Refresh signals coalesce, and a refresh invalidated by a start/stop action waits for the obsolete request to settle before requesting fresh state. Pagehide discards/aborts its client request and retains generation guards. All sync-status requests have a 15-second client timeout. |
| Removing idle polling could hide a run started in another tab | A settled page otherwise has no timer to discover another page's command. | Yes | Successful start/stop commands publish a same-site/user localStorage timestamp signal. Other visible plugin tabs perform one refresh; hidden tabs wait until visible. No job data, credentials or provider names are stored in the signal. Focus refresh remains available if storage is blocked. |
| Active polls resent large success/error arrays | Every response serialized the bounded diagnostic lists, although the UI only consumed them at completion. | Yes | Plugin pollers request `summary=1`, which omits intermediate diagnostic arrays during processing. Final responses retain the diagnostics, and legacy/default requests retain their previous payload. |

The three existing status owners remain mutually scoped: settings owns its page, the wizard owns cloud setup, and the widget owns the custom-domain page. Active work normally checks every five seconds. A terminal bulk status with a still-valid operation lease remains monitored until the lease clears, preserving the startup/configuration safety lock. Polling does not start, stop or retry transfers. DNS/certificate checks are separate workflows and are not changed here.

Verification: **103 admin tests passed**, including eight new policy cases for all three pages, bounded backoff, hidden/offline behavior, one in-flight request, cross-tab refresh and authentication recovery. **235 PHP checks passed**, including summary/default/final payload behavior. The native main-page browser workflow asserts that a failed run generates no further status requests over two simulated minutes; the shared-widget and six-provider cloud-wizard browser workflows also passed. Both PHPStan passes, PHP/JavaScript syntax, translation extraction and whitespace checks passed.

Browser requests and transfer tests were mocked. No production sync or queue was started/stopped.
