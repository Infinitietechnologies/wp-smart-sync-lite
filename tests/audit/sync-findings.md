# Queue, settings, helper and test-tool findings

Audit started 24 October 2026. Existing uncommitted changes are preserved. No commit, staging or push is authorized.

| ID | Status | Fixed? | Trigger and observed result | Root cause | Fix / verification |
| --- | --- | --- | --- | --- | --- |
| SYNC-001 | Fixed; regression passed | Yes | A request caches a lease while another request releases it, then acquisition reports busy despite no database row. A cached previous owner also prevents the real owner releasing its current row. | `acquireSyncLock()` and `releaseSyncLock()` read WordPress's request-local option cache instead of the durable lease. | Lease reads now use SQL, with owner/value compare-and-delete and option-cache invalidation. Both cache regressions pass in `tests/cases/sync_audit2.php`. |
| SYNC-002 | Fixed; regression passed | Yes | A corrupt lock stored as serialized `b:0;` cannot be reclaimed; synchronization stays blocked. | Recovery unserializes then reserializes the value. WordPress serializes false differently, so the conditional delete never matches the original bytes. | Compare/delete the original stored bytes. Serialized-false recovery regression passes. |
| SYNC-003 | Fixed; regression passed | Yes | Releasing a lock whose stored token is an array emits an array-to-string warning; with strict handling it throws from a worker's `finally` block. | The release path casts malformed token data before `hash_equals()`. | Validate the token's string type before comparison; malformed-owner regression passes without changing another owner's value. |
| SYNC-004 | Fixed; regression passed | Yes | A zero/negative TTL returns a lease that is already expired; overflow can also produce an unusable expiry. Another worker can replace it while the caller believes it owns coordination. | Public lock API does not validate duration bounds before adding expiry. | Reject nonpositive and overflowing lease durations before any option write. Duration regression passes for zero, negative and maximum integers. |
| SYNC-005 | Fixed; regression passed | Yes | The legacy `getS3Files()` helper requests a fourth page after continuation tokens cycle A/B/A; without the test guard it can loop indefinitely. | It delegates iteration to an SDK paginator that does not detect S3 token cycles. | Explicit token validation/visited tracking rejects the cycle after three requests, preserving exact returned keys and sizes. |
| SYNC-006 | Fixed; regression passed | Yes | A newer run begins after a reader gets an old pre-token processing snapshot; legacy recovery saves its old snapshot over the new run. | `SMARL_S3SyncSettings::load()` migrated legacy progress with an unconditional option write rather than compare-and-swap. | Recovery now compares the exact read snapshot in SQL, invalidates caches and reloads the winning snapshot after a lost race. Deterministic interleaving regression passes. |
| SYNC-007 | Fixed; regression passed | Yes | Processing progress with an invalid/missing direction repeatedly schedules callbacks that immediately return, leaving the UI running indefinitely. | The loader repaired a missing run token but not an invalid processing direction. | Invalid processing state becomes failed/restartable; UI state is derived from execution status. Invalid-direction recovery regression passes. |
| SYNC-008 | Fixed; regression passed | Yes | Older or malformed progress options can load thousands of diagnostics into polling despite worker-side bounds. | `fromArray()` filtered types but did not retain the worker's 200-error/500-success caps. | Deserialization keeps the latest 200 errors and 500 successes, including the recovery message within the cap. Boundary regression passes. |
| SYNC-009 | Fixed; regression passed | Yes | A database-denied cancellation returns success even though progress remains processing. | Progress `save()` ignored `update_option()` failure, and stop did not check durable cancellation. | Progress writes verify durable serialized data; Stop returns a safe error on failure and cancels pending actions in finally. SQLite trigger regression passes; unchanged saves remain valid. |
| SYNC-010 | Fixed; regression passed | Yes | After another request stops an old autoloaded run, progress reload returns the cached processing snapshot and can reschedule obsolete work. | Clearing the individual option/notoptions caches does not clear WordPress's request-local `alloptions`, which takes precedence for legacy autoloaded options. | Load the original serialized progress directly from SQL, bypassing all option caches. Both the focused stale-alloptions regression and actual WordPress cache regression pass. |
| SYNC-011 | Fixed; regression passed | Yes | A worker's unchanged conditional save returns true even when a concurrent stop replaces its row before the UPDATE executes. | A zero-row UPDATE was accepted solely because the proposed snapshot equaled the earlier read; the current durable row was not rechecked. | Accept a no-op save only after re-reading matching durable bytes. A SQLite BEFORE UPDATE trigger changes progress to idle and ignores the outer UPDATE; the regression now returns false. |

SYNC-001 through SYNC-005 affect `src/Helpers/SMARL_Helper.php`. Reproductions use a real SQLite options table and narrowly enabled request-cache doubles. The first five regressions failed before repair and passed afterward. SYNC-006 through SYNC-009 each failed in a later deterministic pre-fix run; all now pass (combined PHP suite: 182 passed, 0 failed). No cloud services were involved. Later combined results are recorded in the central issue index.

SYNC-010 and SYNC-011 were found during independent review of the repairs, reproduced as two additional failing cases, then fixed. The final combined suite has 184 passing cases. `tests/integration/sync_audit2.php` adds five actual WordPress groups for native cache/SQL lease handling, concurrent migration, autoload cache, bounded recovery and idempotent saves, and denied cancellation with real Action Scheduler cleanup. These use disposable fixtures and block external HTTP.
