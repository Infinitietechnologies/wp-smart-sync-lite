# SmartSync second-audit issue register

Later follow-up: [WordPress compatibility verification](../WORDPRESS-COMPATIBILITY.md) records minimum/latest support and the separately identified WP-COMP-001 initialization repair. The 43-finding tally below belongs to this audit capture.

Review date: 24 October 2026. This register consolidates the second whole-code audit of the existing uncommitted work, now packaged locally as 1.7.3. No commit, staging, push or other Git mutation is authorized by this audit.

The second audit has **43 distinct findings: 10 core, 13 UI/documentation, 9 provider/configuration and 11 queue/helper findings**. **42 are fixed; PRV-008 is partially mitigated and is not fully fixed.** All IDs were independently matched against the four detailed ledgers, excluding repeated references. The Google selection race is counted once as PRV-006, despite its coordinated UI repair.

“Fixed: Yes” means the reported reproduction has a local repair and executable regression evidence. It does not certify every branch, production environment or live cloud workflow. PRV-008's duplicate-allocation/recovery protections are repaired, but remote provisioning still cannot be rolled back atomically.

## Actual-service and coverage boundaries

- No live cloud credentials/accounts, real provider provisioning, public object transfer, production DNS, ACM issuance, CloudFront deployment, billing, quotas or remote destructive behavior were exercised. Actual installed SDK serialization and fake transports validate contracts locally; they do not establish real IAM/storage policies or internet delivery. Native browser AJAX validates browser-to-WordPress wiring while its outbound Bunny calls remain fixtures.
- PRV-008 remains partial: tracked CloudFront resources may remain active if setup is abandoned, and a lost response before an ID becomes known can require manual reconciliation by its stable identity. No atomic rollback or automatic CloudFront disable/deploy/delete sequence is implemented.
- Ambiguous legacy objects without provable target ownership can be retained. Remote deletion remains best effort rather than a durable retry outbox. Live concurrent cloud-policy writers, transfers beyond the lease duration and operating-system parallel scheduling were not exhaustively stress-tested.
- Very large S3 objects beyond single-PutObject limits and enormous accumulated listing manifests are untested scaling boundaries. The Bunny 64 MiB/32 MiB-memory regression proves its specific streaming path and requires PHP cURL; it does not prove arbitrary transfer sizes or network reliability.
- Function-entry counts include only the documented named-method/script/callback populations. They do not mean full statement/branch/path coverage. Fixture PHP/WordPress/browser results do not prove every supported runtime version, object cache, webserver, filesystem or third-party plugin combination.
- Browser lifecycle events were simulated for adversarial BFCache cases; browser retention decisions are not forced. Screen readers, other browser engines, forced high-contrast modes and all locale layouts were not exhaustively executed. Documentation's bundled third-party libraries were not blindly upgraded or represented as a complete vendor vulnerability audit.
